## 0. 一页结论

1. **三层共存**：写定层（主线任务、拉远场景、写定神行节点、主线天启）保证故事走完；纷争层（各幕按周推进的势力纷争事件链）
   让世界在玩家不介入时也自己发展；动态层（女神 GM、NPC 社会、聚落调度器、委托板、叙事导演、运营天启）填充日常与意外。
   仲裁顺序是写定、纷争、动态；下层不得改写上层的保护对象。
2. **一切结果由内核结算**（[框架 8][gf]）：任务完成、链的结局、世界状态写入只来自内核的规则与证据；AI 只在"决策点"与"包装文案"上提议（D-007）。
3. **任务没有硬失败**：主线只有"失败分支"（向前失败），支线与纷争失败或过期即按默认结局写回世界；唯一的游戏结束是回收结局（[框架 12][gf]）。
4. **条件表达式统一为一种语法**：以揭示台账的 `AND`、`OR`、`NOT`、`>=`、`==` 为基线，补 `<=`、`<`、`>`、`!=`、括号、`IN`、`HAS`、`COUNT`；
   分幕文档里的"不低于""且""三取二"在数据层一律改写为这套语法。
5. **世界状态变量进注册表**：一份注册表登记每个变量的类型、范围、作用域、写入者、读取者与别名，台账引用它（Q-011 的倾向）；
   本文给出命名规范与现有不一致的统一建议（第 3.7 节）。
6. **AI 能发布的只有"模板实例"**：首领与官员经意图菜单发布委托与悬赏，女神经其势力内的组织发布委托，女神试炼从规则块库组合；
   AI 只选模板、填区间内的参数、写文案，内核按十余道闸门校验（第 6.5 节）。
7. **幕结束是一次结算**：未结算的链按默认推进到结局，幕出口变量写入后冻结，下一幕按"本幕开头如何读取上一幕"的映射初始化（第 7 节）。
8. **编辑器以可达性为中心**：任务图与事件链时间轴可视化，表达式类型检查，自动检查主线可达、无死锁、出口变量完整、证据可得、奖励预算与降级覆盖（第 9 节）。

## 1. 定位与硬约束

### 1.1 一句话

把写定的主线、按周推进的势力纷争、由女神与众生生成的动态事件，放进同一套"条件、阶段、结算、写回"的数据结构里，
让世界既有作者写好的骨架，又能在玩家缺席时自己往前走。

### 1.2 服务的支柱（[愿景 3][vision]）

| 支柱             | 本系统的贡献                                                             |
| ---------------- | ------------------------------------------------------------------------ |
| 层层展开的世界   | 主线任务与拉远场景按幕推进；幕出口变量把每一层的结果写成下一层的初始条件 |
| 慢慢发掘的龙傲天 | 任务奖励里的"钥"把经历、抉择、羁绊变成开门条件                           |
| 谨慎的强者       | 任务信息只按玩家已知显示；隐性期限、传闻真假、委托人的隐瞒都是玩法       |
| 活着的众生       | 纷争不介入也会发展；NPC 在决策点按立场选择；居民的求助能变成委托         |
| 诸神的棋局       | 女神经组织发布委托、写定神行节点、女神试炼与女神线                       |
| 从一人到一国     | 目标类型从击败、调查延伸到建造、外交、指挥战役、放手                     |

### 1.3 硬约束

| 约束         | 内容                                                                                      | 依据                                        |
| ------------ | ----------------------------------------------------------------------------------------- | ------------------------------------------- |
| 内核裁决     | 任务进度、完成、失败与世界状态写入只由内核结算；AI 不能宣布完成，目标标记完成须有世界证据 | D-007、[框架 8][gf]、[AI 架构 8.3][aia] K12 |
| 降级可通关   | 三层内容在无模型时都必须能运行，主线可完整通关                                            | D-010、[AI 架构 9.5][aia]                   |
| 台账约束     | 任何任务文本、委托文案、事件台词都经揭示台账过滤；同构禁令在第四幕莫伊拉点破之前有效      | [揭示台账 0.2][rl]                          |
| 修正项       | 事件对价格、灾害等的影响只能经注册过的修正项通道                                          | D-013、[经济 7][eco]                        |
| 越约与敌对   | 女神越约每幕至多一次并留蚀痕；对玩家的直接敌对只经化身并受每幕敌对预算约束                | D-026、D-027、D-047                         |
| 叙事导演     | 莫伊拉的导演通道只服务玩家体验，私心只能经常规神权动作实现                                | D-035                                       |
| 不停表       | 模型失败时逐级降级到规则，事件链到点照常兜底                                              | D-036、[NPC 社会 9][npc]                    |
| 世界不等玩家 | 玩家不在场、死亡退回门内期间，事件链照常推进                                              | [框架 12][gf]                               |

### 1.4 不做什么

- 不做重复刷怪的任务堆量（[愿景 8][vision]）：可重复内容只限公会委托板，并受金钱与经验预算约束。
- 不让大模型自由生成任务结构：模型只填模板的终结符文案与区间内参数（依据 [方法论 6.1、6.7][meth]"结构由规则，文案由模型"）。
- 不做"一次点击定结局"的大分支：多路径只在幕级做少量高影响分支，并在下一幕开头汇合（[方法论 4.6][meth]）。
- 不在任务日志里泄露玩家不知道的事：期限、默认结局、隐藏解法只在玩家得知后显示。

## 2. 三类内容的共存

### 2.1 三层

| 层     | 内容                                                                                                 | 谁写                            | 推进方式                                             | 玩家能否错过               | 不介入时           | 来源                                               |
| ------ | ---------------------------------------------------------------------------------------------------- | ------------------------------- | ---------------------------------------------------- | -------------------------- | ------------------ | -------------------------------------------------- |
| 写定层 | 主线任务（第一到第三幕各 13 条）、拉远场景、写定神行节点 `DivineBeat`、锚点台词、主线天启            | 作者                            | 条件加时间窗；必达节点到窗口末由执行者用预写版本兜底 | 不能；剧情必开的门只用时钥 | 由兜底推进         | [一幕 5.1][a1]、[女神 GM 6.5][gm]、[力量 9.4][pow] |
| 纷争层 | 各幕纷争事件链（第一幕 9 条、第二幕 8 条、第三幕 7 条、第四幕 5 条加建国链等）；挂在介入节点上的支线 | 作者写骨架，AI NPC 在决策点选择 | 按周（或季、序、回合、场次）推进                     | 能；错过即走默认发展       | 自行发展到默认结局 | [一幕 4][a1]、[NPC 社会 9][npc]                    |
| 动态层 | 女神动作落地、NPC 社会的纷争种子与求助、聚落事件调度器、公会委托板、叙事导演的巧合与喘息、运营天启   | 系统按模板生成，模型可提议      | 触发条件、冷却、密度                                 | 能                         | 按模板的过期结算   | [城建 10][cb]、[女神 GM 5、8、9][gm]               |

### 2.2 仲裁规则

1. **写定优先**：动态层与纷争层不得以写定受保护的角色、地点、节点前置为负面目标（[AI 架构 8.3][aia] K10 `PROTECTED`）；
   叙事导演不得杀死或救下写定角色、不得改战斗结果、不得交付未解锁的揭示、不得发放超出当前幕阶的物品（[AI 架构 5.9][aia]）。
2. **链内让路**：纷争链某节点的时间窗内，以同一当事人为对象的动态事件延后到窗口之后，或并入该节点作为"外部变量"。
3. **密度上限**：同一聚落同时进行的严重事件不超过 2 件、两件之间至少间隔 7 天（[城建 10.3][cb]）；同地区同类喜剧桥段每日至多 1 次（[认知 10][rep]）；
   两次重大揭示至少间隔约 1 现实小时（[AI 架构 5.9][aia]）；女神的敌对动作受每幕敌对预算约束，且须先有预兆（[AI 架构 5.8][aia] `NEEDS_PRECURSOR`）。
4. **张力计调度**：每个动态事件模板带张力标签；叙事导演按张力计的目标区间（落地 30 到 50、暗面 50 到 75、高潮 75 到 95、拉远 40 到 60，[女神 GM 8.2][gm]）
   在候选中选择开放巧合或喘息，不新增任务。
5. **玩家缺席照常推进**：链的默认发展与动态事件的过期结算不等玩家；玩家回来时从传闻与"本周发生了什么"摘要得知。
6. **降级同构**：三层都以"规则路径 + 预写文本"为底，模型只是增色（D-008、D-010）。

### 2.3 各幕的推进单位

| 幕   | 推进单位                           | 长度                 | 来源                 |
| ---- | ---------------------------------- | -------------------- | -------------------- |
| 序章 | 节拍 P1 到 P16                     | 约半小时             | [序章 1][a0]         |
| 一   | 周                                 | 约 12 周             | [一幕 1.2、4][a1]    |
| 二   | 周                                 | 14 周                | [二幕 4.0][a2]       |
| 三   | 周                                 | 24 周                | [三幕 4.0][a3]       |
| 四   | 季节与"序"（999 年春到秋末）       | 约 3 季              | [四幕 1、4.2、8][a4] |
| 五   | 季节与战役回合 0 到 5              | 999 年冬到 1000 年夏 | [五幕 1、7.1][a5]    |
| 六   | 审理场次（6 场，每场约箱庭一个月） | 1000 年夏到冬至      | [六幕 2.4][a6]       |

所有单位最终换算到内核的游戏日（[框架 6][gf]）。事件链节点用 `clock` 字段声明单位，编辑器统一在游戏日轴上显示。

### 2.4 一个游戏日内的结算顺序（建议）

1. 世界规则结算（经济、生产、人口、疫病、修正项到期）。
2. 写定层：到窗的写定节点与神行节点触发；窗口末仍未执行的必达节点由执行者兜底。
3. 纷争层：到点的链节点推进；决策点开放或按效用兜底；默认发展写入。
4. 动态层：模板触发判定（条件、随机流、冷却、密度）；女神与首领的提议过闸门后落地。
5. 叙事导演：读取张力计，开放巧合或喘息菜单项。
6. 任务进度与传闻：目标进度结算、传闻生成与传播、任务日志与传闻簿刷新。

随机判定一律走内核的确定性随机流，同一存档同一命令序列复现同一结果（[AI 架构 3.3][aia]）。

## 3. 数据对象

本节的字段是概要设计的提案，详细设计时与 [AI 架构][aia] 的数据层对齐。复用主工程 `QuestDef` 的部分见第 11 节。

### 3.1 任务 `QuestDef`

分幕任务表的列（编号、名称、发布者、触发条件、目标、可选解法、奖励含门的钥、对势力与传闻的影响）与主工程 `QuestDef`
（[调研 7.4][inv]）合并为下表：

| 字段                     | 含义                                                                       | 来源                                |
| ------------------------ | -------------------------------------------------------------------------- | ----------------------------------- |
| `id`                     | 稳定编号，规则见第 3.9 节（例 `A1-M06`）                                   | 分幕任务表                          |
| `act`、`kind`            | 所属幕；种类：主线、支线、链节点任务、委托、女神线、女神试炼、同伴线、动态 |                                     |
| `giver`、`turnIn`        | 发布者与交付者：NPC、组织、女神（经组织）、系统                            | 主工程 `giverNpcId`、`turnInNpcIds` |
| `publishForm`            | 发布形式：口头、告示、委托板、神谕、托梦、信件                             | [AI 架构 6.3][aia] `publicForm`     |
| `trigger`                | 可接条件（第 4 节表达式）                                                  | 分幕"触发条件"                      |
| `window`                 | 最早、最晚可接时间（游戏日或周）                                           | 例：M10"第 6 到 9 周"               |
| `stages[]`               | 阶段，见第 3.2 节                                                          |                                     |
| `solutions[]`            | 可选解法，见第 3.3 节                                                      | 分幕"可选解法"                      |
| `rewards`                | 奖励，见第 3.4 节                                                          | 分幕"奖励（含钥）"                  |
| `effects`                | 完成或失败时的世界写入（只限注册表白名单）、传闻种子、声望事件             | 分幕"影响"                          |
| `failure`、`expiry`      | 失败条件与向前失败分支；过期时间与默认结算，见第 3.5 节                    |                                     |
| `ledgerGate`             | 文本分段的台账解锁条件                                                     | [揭示台账 0.1][rl]                  |
| `protected`              | 是否为写定受保护任务（动态层不得使其失败或移除）                           | [AI 架构 8.3][aia] K10              |
| `carryOver`              | 幕结束时是否延续到下一幕                                                   | 第 7.2 节                           |
| `budgetClass`            | 经验与金钱预算档（单任务经验不超过当级升级所需的 25%）                     | [经济 2.3][eco]、[调研 7.4][inv]    |
| `textKeys`、`prewritten` | 文本键与降级档预写版本                                                     | D-010                               |
| `source`                 | 定义它的文档与节号（编辑器回链）                                           |                                     |

### 3.2 阶段 `Stage` 与目标 `Objective`

| 对象        | 字段                                                                                                                                                          | 说明                                                            |
| ----------- | ------------------------------------------------------------------------------------------------------------------------------------------------------------- | --------------------------------------------------------------- |
| `Stage`     | `id`、`enter`（条件）、`objectives[]`、`complete`（全部、任一、计数 N）、`next[]`（条件到下一阶段）、`onFail`、`timeLimit`、`scene`（写定场景）、`checkpoint` | 阶段是有向图，不限于线性；`next` 必须覆盖所有出口（编辑器检查） |
| `Objective` | `type`（第 5 节）、`params`、`count`、`optional`、`hidden`、`evidence`（完成所需的世界证据类型）、`markerLevel`（无、区域、精确）                             | 隐藏目标在玩家得知前不显示；标记精度由信息来源决定              |

例：[一幕 M6 一夜矿道][a1] 的目标"清理上层掘穴虫，发现塌方后有风，一夜打通，找到下层晶脉与走私营地，击败晶背之母"拆为五个阶段，
第三阶段带一夜的时限；第五阶段同时是纷争"税与匪"的节点 d（打通矿道）。

### 3.3 可选解法 `Solution`

| 字段           | 说明                                                                               |
| -------------- | ---------------------------------------------------------------------------------- |
| `id`、`label`  | 解法编号与名称                                                                     |
| `requires`     | 条件：门、物品、同伴、前世之门、关系、知识（例：扳手前世找承重点、夜羽从裂缝侦察） |
| `stagePath`    | 该解法经过的阶段序列                                                               |
| `consequences` | 与其他解法不同的世界写入、传闻模板、关系变化                                       |
| `discoverable` | 玩家如何得知这个解法（同伴提示、传闻、识才之门、无提示）                           |

解法是一等对象，编辑器能对每条解法单独做可达性检查；任务结束后，日志可以显示"还有别的做法"（只显示玩家已知的那些）。

### 3.4 奖励 `Reward`（含门的钥）

| 种类             | 说明                                                                                     | 来源                                                      |
| ---------------- | ---------------------------------------------------------------------------------------- | --------------------------------------------------------- |
| 经验、金钱、物品 | 按预算档；物品按门倾向或装备选择分配                                                     | [经济 2.1][eco]、[复用映射 3.8][reuse] `REWARD_ARCHETYPE` |
| 钥 `keyGrants[]` | `{ doorId, keyKind, keyId }`；`keyKind` 取历钥、物钥、缘钥、择钥、地钥、阶钥、识钥、时钥 | [力量 9.4][pow]                                           |
| 关系与声望       | `trust.<角色>` 增减、势力声望、机构定性                                                  | [认知 5][rep]                                             |
| 证据与史料       | `evidence.<编号>`、史料道具                                                              | [六幕 4.2][a6]、[编年史 12][his]                          |
| 解锁             | 系统、地点、委托板等级、建筑                                                             |                                                           |
| 传闻种子         | 完成方式决定的传闻版本                                                                   | [认知 4][rep]                                             |
| 无               | 合法；例"这是失去的一章"                                                                 | [二幕 A2-M11][a2]                                         |

钥的规则：任务只发放"钥事件"，开门与否由千门系统判定（`thousand_doors.md`，待撰写）；一扇门通常需要 2 到 3 种钥，
剧情必开的门只用时钥（[力量 9.4][pow]），因此主线推进永远不依赖可错过的支线钥。择钥会令另一扇门锁闭，任务的抉择阶段要在界面上
以"这个选择会关上一些可能"的模糊提示告知，不点名门。

### 3.5 失败与过期

| 情形         | 处理                                                           | 例                                                                                                           |
| ------------ | -------------------------------------------------------------- | ------------------------------------------------------------------------------------------------------------ |
| 主线失败     | 向前失败：进入失败分支，剧情继续，代价写入世界状态             | 第三幕战役 0 失败，千军之门仍开但罗恩的成长减半；战役 4 失败进入 `ash_exile`，"游戏不结束"（[三幕 7.4][a3]） |
| 支线失败     | 按失败分支写回，不可重接                                       | 目标人物死亡、互斥抉择                                                                                       |
| 隐性期限     | 写进 `expiry`；玩家只在得知后看到期限                          | 欧文"第 6 周前没人帮他就离开"（[一幕 3][a1]）；托比"第 8 周结束前未获有效救治"（[一幕 7.2][a1]）             |
| 显性期限     | 委托与限时目标显示倒计时                                       | 第四幕挤兑"限定时间内兑现门路运力"（[四幕 8.1][a4]）                                                         |
| 被他人先完成 | NPC 或势力先达成目标，任务转为"已由他人完成"，奖励改为人情或无 | 纷争链默认发展抢先                                                                                           |

| 幕结束       | 未完成且非 `carryOver` 的任务按过期结算                        | 第 7.2 节                                                                                                    |

原则：失败永远是世界状态的一个分支，不是红字的"任务失败"；日志写"后来发生了什么"（第 8 节）。

### 3.6 事件链 `EventChain`

分幕文档的纷争节点表（节点、时机、玩家可做、产出）与 [NPC 社会 9][npc] 的决策点接口合并为：

| 字段                 | 含义                                                                                             |
| -------------------- | ------------------------------------------------------------------------------------------------ |
| `id`、`act`、`title` | 编号（第 3.9 节，例 `A1-D01` 税与匪）                                                            |
| `clock`、`span`      | 推进单位（周、季、序、回合、场次）与起止                                                         |
| `parties[]`          | 当事势力与人物（链内角色可在链启动时具名化）                                                     |
| `nodes[]`            | 节点，见下表                                                                                     |
| `outcomes[]`         | 结局枚举，每个结局声明世界写入；允许可叠加的结局标志（例：税与匪的七种结局可叠加）               |

| 字段               | 含义                                                                                    |
| ------------------ | --------------------------------------------------------------------------------------- |
| `id`、`window`     | 节点编号（例 `A1-D01.d`）与时间窗                                                       |
| `defaultOutcome`   | 玩家不介入时发生什么（世界写入加场景或传闻）                                            |
| `interventions[]`  | 玩家可做的事：挂接的任务或目标；产出三类变化：证据、关系、事实（[一幕 4][a1] 通用规则） |
| `decisionPoints[]` | 点名的 NPC、可选菜单、截止（时间窗末）、兜底效用权重（[AI 架构 3.3][aia]）              |
| `next[]`           | 条件分支到后续节点                                                                      |

例：[一幕 4.1 税与匪][a1] 第 1 到 10 周，节点 a 到 h（调查劫案、护送欧文、骰子屋、打通矿道、维克的账本、旧哨村、对质莫斯、拦截南逃），
不介入时第 10 周莫斯携灰晶南逃或继续在任。

## 4. 条件表达式语法

### 4.1 基线与扩展

基线是[揭示台账 0.4][rl] 的语法：`AND`、`OR`、`NOT`、比较符 `>=`、`==`，变量与标记名直接引用，不使用竖线符号。本文在此之上补充：

| 元素     | 写法                                                                          | 说明                                                                                          |
| -------- | ----------------------------------------------------------------------------- | --------------------------------------------------------------------------------------------- |
| 变量     | `name`、`family.key`                                                          | 例 `church_suspicion`、`trust.shiya`、`evidence.E07`；内置 `act`、`act_week`、`day`、`season` |
| 字面量   | 整数、小数、`true`、`false`、枚举值（裸写的小写标识符，按变量的枚举类型解析） | 例 `a1_oola_fate == cleared`                                                                  |
| 比较     | `==`、`!=`、`>=`、`<=`、`>`、`<`                                              | 枚举只能用 `==`、`!=`、`IN`                                                                   |
| 逻辑     | `NOT`、`AND`、`OR`，优先级依次降低；括号改变优先级                            | 布尔标记可单独作为条件                                                                        |
| 集合     | `x IN (a, b, c)`；`set HAS item`                                              | 例 `wb_ruler IN (edric, cecilia)`                                                             |
| 计数     | `COUNT(e1, e2, ...)` 返回其中为真的个数                                       | "三取二"写作 `COUNT(e1, e2, e3) >= 2`                                                         |
| 取值函数 | `MIN(...)`、`MAX(...)`                                                        | 只此三个函数，避免把数值逻辑藏进条件                                                          |

约束：

- 条件只做比较与逻辑；加减乘除只允许出现在注册表的 `derive` 与初始化映射里（第 7.3 节），不出现在条件中。
- 引用未登记的变量是编辑期错误，不是运行期的"假"；变量未写入时取注册表默认值。
- 求值在内核里确定性进行，不读现实时间，不调用模型。
- "足够""高""较多"之类的模糊阈值不得进入数据，写作时必须给出数字（初值可标"待调"）。

### 4.2 从分幕文档的写法改写

| 分幕写法                 | 数据层写法            |
| ------------------------ | --------------------- |
| 不低于、达到、以上、至少 | `>=`                  |
| 低于、不足               | `<`                   |
| 为、是、=                | `==`                  |
| 不是、不为               | `!=`                  |
| 且、并且、加上           | `AND`                 |
| 或                       | `OR`                  |
| 三取二                   | `COUNT(a, b, c) >= 2` |
| "都已置真"               | 逐个 `AND`            |

### 6.2 NPC 发布委托

1. 首领或官员在议政节拍里从意图菜单选"发布委托"，填参数（目标类型、地点、报酬、期限）与公开文书（[NPC 社会 8.5][npc]）。
2. 内核校验后，委托以模板实例的形式出现在其组织的委托板或告示上；文书是 AI 的表达，真实理由只进审计视图（[AI 架构 6.1][aia]）。
3. 居民的求助：居民在日常中对玩家说"能不能帮我……"，内核把这句求助映射到一个请托模板（护送、寻物、调查、送信），报酬上限是其财产的一部分；
   映射不上就只是对话，不生成任务。
4. 委托完成后的人情、关系与传闻由内核结算，委托人 AI 只负责道谢的措辞。

### 6.3 女神发布委托（经教会与公会）

1. 女神不以自己的名义出现在委托板上：她经由其势力内的组织（教会、商会、竞技场、学院、德鲁伊结社）作为委托方发布，
   凡人只看到组织（[女神 GM 5.2][gm]）。
2. 冒险者公会不属于任何一司（[国家 2.1][nat]）。建议：女神的组织可以作为普通委托方在公会委托板挂单，公会照常抽成；
   这样"女神经教会与公会发布任务"成立，同时公会保持中立。此条待女神 GM 文档确认。
3. 勇者团调度是艾琉恩的专属动作，任务类型为巡礼、讨伐、护送、调查、逮捕（[女神 GM 5.3][gm]）；当玩家同行时，它对玩家表现为一条临时委托。
4. 女神线支线（每位女神一条，[女神 GM 10.7][gm]）是写定骨架加 AI 对话；关键节点是写定神行节点，保证降级档能走通。
5. 女神试炼由 `goddess.trial` 从规则块库组合胜负条件、限制、计分与时限，内核校验难度落在玩家估计战力区间、奖励在当幕奖励表内，
   未知规则块拒绝；奖励可以是钥（预登记的钥槽）、关系、情报与附物加护（[AI 架构 5.15][aia]、[女神 GM 10.8][gm]；"胜场换力量"见[动画提炼 3][anime]）。

### 6.4 叙事导演如何调度节奏

- **输入**：张力计的六项输入（战斗压力、威胁临近、社会紧张、推进停滞、资源压力、神域压力），其中社会紧张读纷争链的升级阶段（[女神 GM 8.2][gm]）。
- **开放规则**：低于目标区间一段时间开放巧合，高于区间开放喘息；导演从菜单中选择（巧合 6 种、喘息 5 种，[女神 GM 8.3][gm]）。
- **可做**：让已存在的任务线索被撞见（旧识路过、传闻抵达、失物与线索、送错的文书）；在时间窗允许的余量内推迟一个链节点（"节拍推迟"）；
  在多个合格的动态事件模板中挑选与当前张力匹配的一个。
- **不可做**：新建任务、改链节点的结局、越过时间窗末、改战斗结果、杀死或救下写定角色、交付未解锁的揭示、发放超出幕阶的物品（[AI 架构 5.9][aia]）。
- **揭示节奏不经模型**：只安排"已解锁未交付"的台账条目，必达条目到期由执行者交付（[AI 架构 5.9][aia]）。
- **每幕的写定巧合**：例如第一幕莫伊拉的巧合每幕一次，序章莫伊拉兴趣 2 以上时两次（[一幕 7.5][a1]）。

### 7.2 幕结算流程

1. **冻结输入**：暂停时钟；新的 AI 提议排队，不落地。
2. **强制结算**：本幕所有未结算的纷争链从当前节点按默认发展推进到结局；进行中的分支按规则兜底选择。
3. **任务清理**：非 `carryOver` 的未完成任务按过期结算；`carryOver` 的任务带入下一幕（例：同伴线、女神线、跨幕追查）。
4. **写出口变量**：按分幕"带入下一幕"一节（[一幕 12][a1]、[二幕 10.2][a2]、[三幕 10.2][a3]、[四幕 11][a4]、[五幕 10][a5]、[六幕 11.6][a6]）写入；
   每个出口变量在所有路径上都必须有值，或在注册表里有默认值（编辑器检查）。
5. **冻结出口**：幕出口变量置只读；之后的变化写到新的活变量上。
6. **快照与摘要**：存档点；生成本幕摘要供 AI 题面使用（"NPC 与女神记得之前发生的事"，[框架 8][gf]），NPC 记忆按规则折叠（[NPC 社会 5.4][npc]）。
7. **推进幕**：`act` 加一；台账解锁重新求值。
8. **过渡**：幕间的时间跳跃由经营与战略层加速消化（[框架 6][gf]），期间领地按委托与自治度规则结算。

### 7.3 下一幕初始化

- 按分幕"本幕开头如何读取上一幕"一节（[二幕 10.1][a2]、[三幕 10.1][a3]、[四幕 4.1][a4]）的映射读取出口变量，派生本幕初值，
  例：`territory_autonomy` 的起点 = 10 + `village_autonomy` × 0.4，市民议会结局再加 10（[三幕 7.2][a3]）。
- NPC 档位重估（[NPC 社会 1.3][npc]）；死亡名单与关系迁移。
- 载入本幕的纷争链、写定神行节点与动态事件模板集合；张力计目标区间切到"落地"。
- 读取规则必须覆盖上一幕的全部出口变量，否则编辑器给"写而不读"警告。

### 7.4 跨幕一致性

- 同一个量只有一个活变量；分幕快照用幕前缀（第 3.7.2 节）。
- 幕出口变量的取值组合要在编辑器里做汇合检查：下一幕的每条主线在所有合法组合下都可推进（第 9.3 节）。
- 回收结局进入"下一期"：世界状态、等级、国家、关系、证据全部重置，只保留五项（既视、回声之门、识才之门开局即开、硬币的划痕、
  眠鳞碑底座刻痕，[六幕 13][a6]）；台账解锁全部重置（[揭示台账 0.2][rl] 规则 4）。

## 9. 编辑器需求

### 9.1 可视化

| 视图         | 内容                                                                                                   |
| ------------ | ------------------------------------------------------------------------------------------------------ |
| 任务图       | 阶段为节点、分支为边、解法为着色路径；节点上显示目标、条件、奖励与世界写入                             |
| 事件链时间轴 | 横轴为游戏日（按周、季、序、回合、场次换算），纵轴为当事方泳道；节点的时间窗、默认发展、介入点与决策点 |
| 幕总图       | 一幕之内的主线、纷争链、写定神行节点、台账条目的解锁与揭开位置，画在同一时间轴上                       |
| 变量依赖图   | 谁写、谁读；出口变量到下一幕读取的连线                                                                 |
| 证据图       | 第六幕证据的取得路径与指向的防线                                                                       |

### 9.2 编辑辅助

- 表达式编辑器：自动补全变量与枚举值，类型检查，引用未登记变量即报错；分幕写法（"不低于""三取二"）一键改写为第 4 节语法；废弃别名提示规范名。
- 模板编辑：动态事件模板与委托模板的参数区间、钥槽、白名单写入。
- 文本：文本键、台账分版本、降级预写版本并排编辑。
- 来源回链：每个对象的 `source` 字段可跳回定义它的文档与节号。

### 9.3 自动检查

| 检查     | 内容                                                                                           |
| -------- | ---------------------------------------------------------------------------------------------- |
| 主线可达 | 从幕初始状态出发，在上一幕出口变量的所有合法组合下，主线都能推进到幕收束点（向前失败分支存在） |
| 无死锁   | 每个阶段都有出口（完成、失败分支或过期）；每条链都能在幕结束前结算                             |
| 出口完整 | 幕出口变量在所有路径上被写入或有默认值                                                         |
| 读写配对 | 读而不写报错，写而不读警告                                                                     |
| 门与钥   | 每扇门至少有一个钥来源；剧情必开的门只用时钥；互斥门不会同时成为主线必需                       |
| 证据可得 | 第六幕每件证据至少有一条取得路径；真结局所需的最低证据组合至少在一条路径上可达                 |
| 台账     | 每条线索的解锁条件可满足；揭开不早于解锁；任务文本不引用未解锁线索                             |
| 预算     | 每幕经验、金钱、物品投放不超过预算（[经济 2.3][eco]）                                          |
| 保护     | 动态模板不以写定受保护对象为负面目标                                                           |
| 降级覆盖 | 每个 AI 决策点有兜底，每个文本键有预写版本                                                     |
| 命名     | 变量、编号符合第 3.7.2、3.9 节                                                                 |

### 9.4 推演

- 无玩家推演：世界自行发展到每条链的默认结局，检查世界是否"活"（[框架 15][gf] 垂直切片假设 2）。
- 策略推演：全介入、全不介入、随机介入等策略机器人在多个随机种子下批量跑，统计结局分布与出口变量组合（[路线图 6.1][road] W3 的"可达性与无死锁检查"）。
- 推演使用与游戏同源的内核结算，不调用模型；推演种子入回归集（[方法论 6.7][meth]）。

### 9.5 工具位置

本作编辑器是数据工具（地图以俯视格子编辑逻辑层与空间层，外观层按表单编辑），与天启工作台同在 `editor/` 下（[AI 架构 5.1][aia]）；
主工程的世界编辑器是 3D 视口，只借鉴其文档校验思路（[调研 8.2][inv]）。

## 12. 风险与对策

| 风险                             | 对策                                                                           |
| -------------------------------- | ------------------------------------------------------------------------------ |
| 纷争链组合爆炸，下一幕无法初始化 | 出口变量收敛为少量枚举；下一幕开头汇合；编辑器做组合推演                       |
| AI 生成的委托泛滥、重复、跑题    | 模板白名单、密度与冷却、重复度检查；导演只开放菜单不新建任务                   |
| 玩家错过关键线索                 | 必达揭示由执行者交付；导演的"传闻抵达""失物与线索"把线索送到眼前；主线只用时钥 |
| 隐性期限让玩家挫败               | 期限前必有预兆与传闻；失败写成世界分支并给"后来发生了什么"                     |
| 变量命名漂移                     | 注册表加命名检查；废弃名登记别名                                               |
| 降级档体验断崖                   | 写定层与预写文本按台账分版本；推演同时跑降级档                                 |
| 不在场结算显得不公平             | 结算公式与输入在日志里可追溯（[RTS 7.3][rts]）；摘要说明原因                   |
