# 技术架构（概要）

> 本文定义《箱庭纪》的技术分层、确定性内核、系统接缝、数据、存档、客户端、编辑器与测试策略。
> 它是实现阶段的契约：代码结构与本文冲突时，先改本文再改代码。
> 上游：`../40_design/game_framework.md`、`../00_vision/decision_log.md`、`reuse_map.md`、`art_pipeline.md`、
> `../10_research/ai_npc/comparison_and_plan.md`。AI 部分的细节见 `ai_architecture.md`；大模型提供方与密钥见 `llm_providers.md`；
> 桌面壳、存档容器、性能、本地化与发布见 `release_engineering.md`；无模型时的内置 AI 见 `../40_design/systems/builtin_ai.md`。

## 1. 目标与约束

1. **一个内核，多种玩法**：RPG、城建、RTS、SLG 跑在同一个确定性模拟内核上，共用时钟、随机源与世界状态。
2. **确定性**：固定 20Hz tick；所有随机走种子化的 `Rng`；模拟层禁止 `Math.random`、`Date.now`、`performance.now`。
   同一种子 + 同一输入序列 = 同一世界（沿用主工程的确定性原则）。
3. **大模型可选**：AI 只产出结构化提议，以"带 tick 的命令"进入内核并被记录，重放时不调用模型；
   大模型由玩家自配（D-067）；无模型时由内置 AI 驱动全部角色，游戏完整可玩（D-007、D-010、D-068）；模型连续失败时逐级降级到内置 AI，不全局停表（D-036）。
4. **数据驱动**：内容是可被编辑器读写的数据，带校验；新增内容不改代码。
5. **纯逻辑可测**：内核、系统、AI 编排、游戏流程不依赖 DOM，可在 Node 中由测试直接运行。
6. **依赖极少**：沿用主工程工具链（TypeScript strict、Vite、Vitest、Biome）；运行时依赖只有 HD-2D 场景渲染用的 `three`
   （与主工程同版本，D-058）；官方 Claude SDK 只在开发服务的 Node 侧使用，不进发布包（D-059）；桌面壳复用仓库根目录的 `electron` 与 `electron-builder`，
   `steamworks.js` 只打进 Steam 构建（`release_engineering.md` 第 2.2 节）；不随意新增。
7. **模块优先**：每个系统是自己的目录与接口，协调器保持薄（沿用主工程"不让协调器长胖"的原则）。

依赖方向只能向下。`core/`、`content/`、`systems/`、`ai/`、`game/` 禁止引用 DOM、Canvas、Three.js 与浏览器全局；
由架构守卫测试扫描保证（仿照主工程 `tests/architecture.test.ts` 的做法）。

发布版（桌面壳）在客户端之外还有主进程与大模型网关（utility 进程）：客户端经 `src/platform/` 的 `PlatformHost` 访问存档、设置与大模型；
开发服务中间件只在开发期存在，发布版不带（第 9 节；进程分工见 `release_engineering.md` 第 2 节）。`src/platform/` 只被 `src/client/` 引用，
`core/`、`systems/`、`game/`、`ai/` 不得引用它（桌面壳骨架 PK-M0-21 把这条并入架构守卫的分层检查）。

## 4. 确定性内核

### 4.1 时钟

| 常量             | 值                     | 说明                                             |
| ---------------- | ---------------------- | ------------------------------------------------ |
| `TICK_HZ`        | 20                     | 与主工程一致                                     |
| 每 tick 游戏时间 | 3 秒                   | 游戏内 1 天 = 28800 tick = 1 倍速现实 24 分钟（D-070） |
| 日历             | 圣历年、季、周、日、时、分 | 一周 7 日，一季 13 周（91 日），一年四季 364 日；开场：圣历 998 年春第 1 日 06:00（`../40_design/progression_and_pacing.md` 第 13.1 节） |

加速（个人层脱战时的 2x、4x；经营与战略视图的慢、中、快三档，D-050、D-070）通过"每帧推进多个 tick"实现，不改变 tick 的语义；
加速时 NPC 的模型决策自动降频，女神规划在途保持 1 倍速至多 20 现实秒（`ai_architecture.md`，D-079）；各档的 tick 预算与分片见 `release_engineering.md` 第 6.4 节。

### 4.2 随机流

- `Rng` 为种子化的确定性生成器，状态可序列化。
- 每个系统使用自己的命名流（`combat`、`npc`、`economy` 等），彼此的抽取顺序互不影响，降低系统间的耦合与回归风险。
- 新增随机用途时在本系统内新增子流，而不是从别的系统借流。

### 4.3 世界状态与切片

- 世界是一个可序列化的纯数据对象：元信息（种子、版本、tick、幕次、剧情标记）、随机流状态、ID 计数器、各系统切片、近期事件环。
- 各系统用 TypeScript 模块扩充（module augmentation）在 `core` 声明的 `WorldSlices`、`EventMap`、`CommandMap`、`ContentMap`
  接口上登记自己的类型。这样核心不需要认识每个系统，系统之间也能获得完整类型检查。
- 规则：一个系统只写自己的切片；读别的系统用该系统导出的查询函数；跨系统的写操作走事件或该系统导出的"端口函数"。
- 实体字段 `alive`、`tags`、`speed`、`move`、`intent` 只由世界系统写，其他系统调 `src/systems/world/ports.ts` 的端口（`setLife`、`setTagValue`、`setTag`、`haltEntity`、`setMoveSpeed`）；
  架构守卫扫描 `src/systems/`（世界系统除外）里对这些字段的赋值（`release_engineering.md` 第 13.1 节）。

### 4.4 事件

- 系统在 tick 内发出事件；当 tick 末尾按发出顺序派发给订阅者（按系统顺序），订阅者可再发事件，设单 tick 上限防止死循环。
- 事件同时进入近期事件环，供 UI、认知系统（目击）、审计与调试使用。
- 事件是"已经发生的事实"，只能由内核与系统发出，AI 不能发事件。

### 4.5 命令

- 玩家输入与 AI 提议都转为命令，排队到下一个 tick 开始时按序执行。
- 每个命令由所属系统的处理器校验并执行，结果是"成功"或"拒绝 + 原因码 + 可读原因"。可读原因写回提议者（AI 会话据此自我修正，沿用 my_ai_town 的做法）；
  可读原因是 `TextRef`（文本键加参数，`implementation_conventions.md` 第 8 节）。
- 需要即时反馈的界面（例如建筑摆放预览）调用系统导出的纯查询函数，不经命令队列。

### 4.6 系统接口与相位顺序

每个系统提供：`id`、`order`（相位）、`init`（创建切片）、可选 `resume`（恢复已加载切片）、`tick`、命令处理器表、事件订阅表、查询函数。

`Engine.resume` 在首条命令或 tick 之前按相位调用各所有者的 `resume`，然后结算其事件；
`resumeGame` 与 `replayFrom` 复用此入口。它不重跑 `init`。恢复钩子只能迁移所属切片，
必须幂等且确定，不消耗随机流、不请求模型。恢复期旗标读写同样经过注册表守卫。

### 4.7 存档与重放

- 存档拆成"当前快照"与"只增不改的历史流水"（事件摘要、AI 决策记录、过完的日子），借鉴 my_ai_town 的拆分，避免快照无限增长。
- 事件摘要之外，为每名有名 NPC 有界保留与玩家相关的原话事件（第六幕"众生之声"与 NPC 记忆的数据来源），上限与淘汰规则见 `ai_architecture.md`。
- 存档带版本号与迁移函数，旧存档的回归样本放进测试夹具。
- 存档容器（槽位头、按哈希寻址的分块文件、写入顺序与原子性、逐版本迁移、损坏检测与恢复、云同步、铁人规则）见 `release_engineering.md` 第 5 节；存档兼容承诺从 M2 开始。
- 重放：初始世界 + 命令日志（含 AI 提议的 tick 与内容）即可完整复现一局，不调用模型。用于调试、录像与平衡回归。

## 5. AI 桥（概要，细节见 `ai_architecture.md`）

```
系统需要决策 -> 内核写入决策请求，并预先算好兜底行为（到期未得到提议则执行兜底，保证世界不停；截止前的默认状态是"暂不决策"）
             -> 若该角色启用模型：向 AI 层提交请求（角色、版本号、题面规格、输出模式、可用动作）
AI 层（异步）-> 题面清洗与预算检查 -> 调用提供方 -> 解析与模式校验 -> 产出提议
游戏编排     -> 提议作为命令进入下一 tick；版本号过时则作废并重新观察；执行结果写回会话
重放日志     -> 记录（tick, 提议）
```

## 6. 内容数据

- 数据放 `data/` 下的 JSON 文件，每类内容在 `content/` 中有模式与校验器（不引第三方校验库，手写轻量校验）。
- 物品分可堆叠商品与带实例的物品（D-072）：持有记录 `Holding.items` 拆为堆叠与实例两部分，`ItemDef` 带 `procs`、`set`、`sed`、`use.group`（`implementation_conventions.md` 第 6 节）。
- 内容类型（首批）：职能与技能、怪物、物品、门与钥、NPC 人设卡、势力、地点与地图、建筑、兵种、国家与省份、女神人格卡、任务与事件链、对话树（序章降级版等）、世界知识条目（带知识层级与揭示阶段标签）、传闻模板。
- 每条世界知识带两个标签：知识层级（凡人常识到神知）与揭示条件（揭示台账的条件表达式），AI 题面组装时按此过滤。
- 编辑器通过开发服务写回 JSON；内容校验测试保证所有数据合法、引用完整、ID 唯一。
- 系统代码不写内容 ID：要用到某张图、某个地点、某位女神、某个国家时，按数据声明的职能或字段去查（`release_engineering.md` 第 13.2 节，内容 ID 守卫）。

## 7. 客户端

- 渲染：HD-2D 三维场景（D-003、D-058），沿用 my_ai_town 的做法：Three.js 正交斜俯视相机、像素贴图地面与立体房屋、
  朝向镜头的像素立牌、光照图与太阳阴影、电影化后期；规格见 `art_pipeline.md` 第 2 节。
  - `src/client/hd2d/`：纯逻辑模块（`view.ts` 相机与视角、`style_packs.ts` 风格包、`daylight.ts` 时刻光照、`layout.ts` 建筑外壳与墙格、
    `textures.ts` 墙面与屋面贴图、`ground.ts` 地面与水体遮罩、`lightmap.ts` 静态光照图、`standee.ts` 立牌深度、`quality.ts` 画质档）
    在 Node 中测试；`shaders.ts`、`materials.ts`、`scene_builder.ts`、`entities.ts`、`post.ts`、`hd2d_renderer.ts` 依赖 Three.js 与 DOM；
    `index.ts` 导出 `createWorldRenderer`（建 HD-2D 渲染器，失败时退回平面渲染）。
  - `src/client/render/renderer.ts` 定义 `WorldRenderer` 接口（`setMap`、`render`、`hitBoxes`、`screenToGround`、`setQuality`）；
    `src/client/render/flat_renderer.ts` 是 Canvas2D 俯视平面渲染，作为降级档（无 WebGL 或玩家选"平面"画质时使用）。
    两种渲染器读同一份 `GameView`，切换不影响逻辑。
  - 帧调度：`src/client/render/frame_scheduler.ts`（纯逻辑核心）按脏原因与场景各部分的变化签名决定每帧画不画；`requestAnimationFrame` 循环照常推进内核与输入，
    只在需要时调用渲染器，暂停时一帧不画（`release_engineering.md` 第 6.3 节）。
  - 画质档：超高、高、中、低、平面（D-078）；首次启动按微基准与显卡名选初始档，按 GPU 计时的自动降档在 Beta 上线、每局至多两次（`release_engineering.md` 第 6.7 节）。
    画质档只减观感，不减玩家据以行动的信息（`art_pipeline.md` 第 2.11、2.12 节）。
- 地图外观层：地图文档在逻辑层与空间层之外有外观层（`style` 风格包、`looks` 逐地点建筑外观、`decor` 装饰），
  类型与编号表在 `src/systems/world/look.ts`；内核不读，只有渲染器读；内容校验检查其引用（`art_pipeline.md` 第 5.1、5.2 节）。
- 素材：美术全部 AI 生成（D-018），导入管线按每米 16 像素量化、按风格包调色板收色后打成图集（`art_pipeline.md`）；人物是纸娃娃部件帧图组合（`src/client/sprites/`），
  有名角色另有头像与半身立绘（D-078）；程序化绘制只作占位与平面降级；不加载 GLB（`art_pipeline.md` 第 3、6 节）。音频见 `../40_design/audio_direction.md`。
- 客户端只读世界：通过 `GameView` 查询接口读取（相当于主工程的 `IWorld` 接缝），只通过命令改变世界。
- 图层：地面与水、建筑（屋顶可掀开）与独立墙块、立牌（人物、怪物、树、石、装饰，按"竖直立在脚下"的深度规则遮挡）、
  特效与天气、覆盖层（名字、头顶标记、气泡、浮字、提示，位置由三维投影得出）、HUD 与窗口。
- 窗口：角色与技能、千门回廊、背包与装备、任务、传闻簿与声望、地图、同伴、商会、领地、战场、大陆、女神与神之记录、存档。
- 文本：内核与系统只发文本键加参数，客户端按字符串表渲染；中文为源语言，1.0 发行简体中文（D-077，`implementation_conventions.md` 第 8 节、`release_engineering.md` 第 8 节）。

## 8. 编辑器与可视化审核工作台

| 工具         | 用途                                                                                                     |

| 内容编辑器   | 按模式生成表单，编辑各类 JSON 数据，实时校验与引用检查                                                   |

## 9. 开发服务与发布版的大模型通道

开发时由 Vite 中间件提供（只在开发期存在，发布版不带）：

- `/api/llm`：开发期的模型调用代理（`tools/llm_proxy.ts`），密钥只在开发机的环境变量里，客户端不接触密钥。
- `/api/data`：编辑器写回 `data/` 下的 JSON。
- `/api/audit`：追加 AI 审计记录到本地日志。
- `/api/assets*`：素材审核台的列表、采用与审核决定（`tools/assets/review/`），写 `assets/manifest.json` 与 `assets/review_log.jsonl`；发布包扫描同样不得出现。

运行时代码经 `src/ai/` 的 `LlmTransport` 发请求，三种实现：`IpcTransport`（桌面，经 `PlatformHost.llm`）、`LocalHttpTransport`（网页试玩，只连本机服务）、
`DevProxyTransport`（开发服务 `/api/llm`，只在 `import.meta.env.DEV` 下引入，生产构建摇树去掉）；发布包扫描不得出现 `/api/llm`（`release_engineering.md` 第 13.9 节，RE-02）。

发布版没有模型代理，也不设官方代理（D-067）：

- **桌面版**：大模型请求经桌面壳主进程转交网关（utility 进程）；网关在本次请求的作用域里解密玩家存于系统钥匙串的密钥，经 `src/ai/providers/` 的适配器调用玩家配置的提供方，
  流式结果经 `MessagePort` 回到渲染进程（`release_engineering.md` 第 2.4 节、`llm_providers.md` 第 2、7 节）。渲染进程与游戏逻辑从不经手密钥。
- **网页试玩版**：不接受云端密钥，只允许浏览器直连玩家本机的模型服务（`llm_providers.md` 第 6.2 节）。
- **无模型**：未配置或全部关闭时由内置 AI 驱动（`../40_design/systems/builtin_ai.md`），游戏完整可玩。
- **天启与远程配置**：随内容版本发布；另有玩家可关的签名远程源，远程内容到达时记为一条命令（进入重放日志），细节见 `ai_architecture.md` 第 5.10 节（AQ-05）。

## 11. 测试策略

1. 架构守卫：扫描纯逻辑目录，禁止 DOM 引用与非确定性 API。
2. 确定性：同种子同命令序列运行 N tick，世界快照哈希一致；存档读回后继续运行与不中断运行结果一致。
3. 系统单元测试：每个系统的规则与公式。
4. 内容校验：全部 JSON 合法、引用完整。
5. 无模型通关：无头运行规则自动玩家（`src/game/autoplay/`，D-071）从序章走到结局，作为垂直切片与每次大改动的硬性验收（D-010、D-068）；多种子矩阵见 `release_engineering.md` 第 10.2 节。
6. 揭示台账：给定幕次，AI 题面中不得出现未解锁知识。
7. 客户端纯逻辑：HD-2D 的纯逻辑模块（相机、风格包、光照、建筑布局、立牌深度、画质档）、帧调度器与地图外观层的引用校验在 Node 中测试。
8. 完整的套件总表（存档迁移与损坏、浏览器与桌面端到端、截图回归、性能回归、模型路径的模拟与回放、11 个结局的自动验证）与流水线见 `release_engineering.md` 第 10、11 节；
   本地全量门 `npm run gate`（`tools/gate.ts`）依次运行全部步骤并如实汇总退出码。
