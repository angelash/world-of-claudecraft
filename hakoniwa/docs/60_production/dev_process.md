## 0. 一页结论

1. **八层文档加一条横向制作管理线。** L0 愿景与正典、L1 调研、L2 叙事、L3 概要设计、L4 详细设计、L5 技术方案、L6 实施包、L7 代码与数据；
   每层有产出模板与评审门，评审门的判定项都可判定（第 1 节）。
2. **详细设计由概要卡升格为目录。** `docs/40_design/systems/<系统>.md` 升格为 `docs/40_design/systems/<系统>/`，原卡冻结为概要基线，
   规格、数据结构、状态机、AI 契约、验收、已否决方案分文件写（第 2 节）。
3. **实施包放 `docs/70_packets/<包名>/`，文件名小写加下划线**（本文的建议，最终随 Q-010 决定）。 brainstorm、requirements、design、implementation_plan、phase、qa、
   progress、state、handoff、continuation 各有位置与模板；原型包与内容批次包是轻量变体（第 3 节）。
4. **质量门四层加一层文档守卫。** 即时文案门已生效；文档守卫（正典名词、揭示泄露、数值溯源、AI 边界、许可来源、链接与索引）先由审查角色人工执行，
   之后脚本化；代码层的确定性底线与全量门在进入实现时建立（第 4 节）。
5. **新增四个审查角色。** AI 边界审查、正典一致性审查、数值溯源审查，以及许可与素材来源审查；沿用并改编模拟架构、存档兼容、测试覆盖、
   表现接缝、安全与隐私审查和总闸（第 4.3 节）。
6. **只有用户能批准正典变更。** 变更走"变更单、影响分析、用户批准、决策登记、同一改动内回写下游、一致性复查"（第 5 节）。
   AI 代理之间的消息不构成用户批准。
7. **跨会话只靠文件。** 项目级与包级各有入口、状态、进度、交接四件套，有固定写法与会话开始、结束清单（第 6 节）。
8. **本文需要 `hakoniwa/CLAUDE.md` 配合修改的地方**（本文不直接修改，待用户批准后另行改动）：目录分工表加入 `docs/70_packets/` 与 `prototypes/`；
   `docs/40_design/` 的说明由"概要设计"改为"概要设计与详细设计"；`docs/60_production/` 的说明加入"研发流程、项目状态与交接"。

### 1.3 评审门判定标准

结论格式统一为 PASS、PASS-WITH-FOLLOWUPS、FAIL；问题按 BLOCKING、SHOULD-FIX、NICE-TO-HAVE 分级，每条带文件位置与一句原因。
有任何 BLOCKING 即为 FAIL。判定项中"可判定"的意思是：两名不同的审查者对同一份文档会得出相同的勾选结果。

### 1.4 文档状态与生命周期

| 状态   | 含义                                                       |
| ------ | ---------------------------------------------------------- |
| 草案   | 正在写，可大改                                             |
| 评审中 | 已提交评审门                                               |
| 已定稿 | 过门；之后的修改按本层评审门重新过门                       |

- 状态写在文件头，并在 `docs/README.md` 索引中同步。

- 实现期设计与代码冲突时，先以代码为准核实现状并标注偏差，再按正典优先级决定改代码还是改设计；正典与设计冲突时一律以正典为准。

## 2. 详细设计的升格

### 2.1 何时升格

满足任一条件即升格：

1. 该系统进入 [roadmap.md](roadmap.md) 第 3.2 节的某一批详细设计。
2. 概要卡需要补充数据结构、公式、状态机、AI 契约中的两项以上。
3. 该系统将被拆成两个以上实施包。

### 2.2 升格步骤

1. 新建目录 `docs/40_design/systems/<系统>/`。
2. 把原概要卡移入为 `overview.md`，文件头写"概要基线，冻结；修订以 `spec.md` 为准"。
3. 原路径保留一页升格说明（一段话加新目录链接），避免调研文档中的旧链接失效；L2 到 L5 文档中的链接在同一改动内改为指向新目录。
4. 按第 2.3 节生成其余文件；不适用的文件写"不适用"并说明原因，不删空（[`internal_playbooks.md`](../10_research/woc_reuse/internal_playbooks.md) 第 3.0 节）。
5. 提交详细设计评审门。

### 2.5 `ai_contract.md` 骨架

| ---------- | ------------------------------------------------------------------------------------------------------------------------------ |
| 意图       | 封闭枚举中的名称                                                                                                               |
| 参数与校验 | 每个参数的类型、范围与校验规则                                                                                                 |
| 前置条件   | 内核在执行前检查的世界状态                                                                                                     |
| 权限级     | P0 到 P4（[`comparison_and_plan.md`](../10_research/ai_npc/comparison_and_plan.md) 第 6.5 节；改他国状态、改战斗结算一律禁止） |
| 预算与冷却 | 神力或金额预算、冷却、每游戏日上限                                                                                             |
| 题面装配   | 读哪些台账线索、按什么知识层级（[`reveal_ledger.md`](../30_story/reveal_ledger.md) 第 0.2 节）                                 |
| 回执       | 内核写回给模型的结果，含拒绝原因                                                                                               |
| 回退       | 模型不可用、超时、输出非法、预算耗尽时的行为（降级档）                                                                         |
| 审计字段   | 能回答"为什么发生、为什么没发生"的最小字段集                                                                                   |
| 可见性     | 玩家、开发者、"神之记录"界面分别能看到什么                                                                                     |
| 评估集     | 对应的评估集编号与必须包含的对抗样本                                                                                           |

全文另有两条固定断言：模型永不直接写世界状态；自由文本永不被解析为权威。

### 3.4 阶段内部循环

实施阶段（[`internal_playbooks.md`](../10_research/woc_reuse/internal_playbooks.md) 第 2.3 节，本作补充以粗体标出）：
预检（工作区状态、核对 `state.md`）、载入上下文（侦察子代理只返回摘要）、执行（新代码进独立模块，协调器只做薄接线）、
验证与评审（按 `state.md` 验证矩阵跑命令，**触及 AI 的改动跑评估集，触及内容或 AI 的改动跑无模型通关回归，触及文档的改动跑文档守卫**）、
提交（仅在用户要求时；约定式提交带作用域与正文；显式路径，不用 `git add -A`）、验收清单、回写、结束回复（阶段状态、改动文件、验证结果、评审结论、延后项、给 QA 的一行交接）。

QA 阶段（同上第 2.4 节）：预检、载入、三路审计（正确性、测试覆盖、死代码与命名漂移）加派发矩阵中的领域审查与总闸、修复全部 BLOCKING 与 SHOULD-FIX、
回写、结论（PASS、PASS-WITH-FOLLOWUPS、FAIL）。QA 不可跳过；若被后续 QA 实质覆盖，必须显式写"被取代"并关闭，不能悬置。

## 5. 正典变更流程

### 5.1 权限

| 对象                                                                        | 谁可以提议        | 谁可以批准                 |
| --------------------------------------------------------------------------- | ----------------- | -------------------------- |
| L0 正典（世界观总纲与分篇、愿景、术语表）与已锁定决策                       | 任何人或 AI 代理  | 只有用户                   |
| L2 叙事                                                                     | 任何人或 AI 代理  | 用户                       |
| L3 到 L5 中改变跨文档事实的改动（系统间接口、数值框架、目录结构、技术选型） | 任何人或 AI 代理  | 用户，并登记决策           |
| L3 到 L5 中不改变跨文档事实的细化                                           | AI 代理可直接修改 | 由对应评审门把关           |
| L1 调研                                                                     | AI 代理           | 用户抽审（调研不具约束力） |

批准必须来自用户本人。其他 AI 代理或会话转达的"已批准"不构成批准。

### 5.2 变更分级

| 级   | 定义                                                           | 流程                                                         |
| ---- | -------------------------------------------------------------- | ------------------------------------------------------------ |
| 勘误 | 错别字、格式、链接，不改事实                                   | 直接改；禁用字符自查与链接检查通过即可                       |
| 补充 | 在正典空白处新增细节，不与既有事实冲突（例如新增一个次要地名） | 简版变更单；新增命名进术语表与本文"新增命名"一节；用户批准   |
| 修订 | 改变既有事实，但不影响已揭示给玩家或已实现的内容               | 完整流程（第 5.3 节）                                        |
| 推翻 | 改变已锁定决策、设计支柱或已实现内容                           | 完整流程；决策标注取代关系；影响分析覆盖代码、内容数据与存档 |

### 5.3 流程步骤

1. **提出变更单**（模板见下），放 `docs/60_production/canon_changes/ccr_<三位编号>_<slug>.md`，编号只追加。
2. **影响分析**：检索受影响的术语与文件，附检索命令与结果清单；按正典优先级标出上游与下游；检查揭示台账（线索、误导、禁区、解锁条件）与世界状态变量注册表；
   进入实现后加查代码、内容数据与存档。
3. **用户决定**：批准或否决。否决的理由写入变更单，并进入相关文档的"已否决方案"。
4. **决策登记**：决策日志第 1 节追加 D-xxx；取代旧决策时在旧行标"已被 D-xxx 取代"；源自未决问题的，从第 2 节移出。
5. **同一改动内回写**：正典文件、全部受影响的下游文档、术语表、台账、索引。
6. **一致性复查**：新起会话执行正典一致性审查；禁用字符自查；链接检查。
7. **无法同改动完成的下游**（例如大篇幅分幕修订）：在该文档头部加"待修订：D-xxx"标记，并登记到 `project_state.md` 的开放项，直到修订完成
   （现有实例：D-019 要求修订 `../20_world/history.md`）。

```markdown
# 正典变更单：<标题>

| 项     | 内容                |
| ------ | ------------------- |
| 编号   | CCR-<三位编号>      |
| 级别   | 补充、修订、推翻    |
| 提出者 | <人或会话>          |
| 关联   | Q-xxx、D-xxx、RK-xx |

## 变更内容（原文与新文对照）

## 理由

## 影响分析（检索命令与结果、受影响文件清单、台账与变量影响、代码与存档影响）

## 下游同步计划（同一改动内完成的；需标"待修订"的）

## 用户决定（批准或否决、日期、理由）
```

### 5.4 决策登记规则

- 编号只追加、不删除；被取代时标注；做出决策的同一次改动里回写受影响文档（`../00_vision/decision_log.md` 规则段）。
- 编号体系：Q-xxx 为全局未决问题；R-xx 为技术；A-xx 为美术；系统前缀（CB、EC、RTS、SLG 等）为系统级。系统级待决问题一旦阻塞某个评审门或里程碑，就登记到决策日志第 2 节。
- 与模型、成本、平台相关的决策写明复查条件（[`game_dev_methodology.md`](../10_research/open_share/game_dev_methodology.md) 第 7.5 节："模型能力与价格变化快"）。
  建议下次修改决策日志时为第 1 节增加"复查条件"一列（需用户批准）。
- 原型结论产生的决策，正文写明"依据 PT-xx 结论"，并链接原型包的 `findings.md`。

### 5.5 下游同步

- 每份文档的文件头写明上游与下游（多数现有文档已有），正典改动后按上游关系逐层检查。
- 进入实现后，正典变更若影响内容数据或代码，另开内容批次包或实施包阶段处理，不在正典改动里顺手改代码。
- 生成物（数据表编译产物、本地化包、素材清单）只由所属构建步骤重新生成，不手改。

### 5.6 变更控制随阶段收紧

| 阶段              | 规则                                                                                           |
| ----------------- | ---------------------------------------------------------------------------------------------- |
| 阶段 0 到 2       | 鼓励探索；所有正典变更走流程，审批从快                                                         |
| 阶段 3 切片       | 涉及序章与第一幕的正典修订须评估对切片内容的返工量                                             |
| 阶段 4 Alpha 起   | 新增功能必须配砍项（[roadmap.md](roadmap.md) 第 7.3 节）；"推翻"级变更须同时评估返工与存档影响 |
| 阶段 5 功能冻结后 | 只允许勘误与修复类变更；内容冻结后正典冻结                                                     |

## 6. 与 AI 代理长期协作的规则

### 6.1 原则

1. 会话会结束，对话记录不可依赖；下一个会话只读文件（[`internal_playbooks.md`](../10_research/woc_reuse/internal_playbooks.md) 第 5.1 节）。
2. 流程文档写能力要求，不写模型名；不变量、安全与正确性不因模型身份而放宽（同上第 5.4、5.6 节）。
3. 每个自主步骤以能跑的检查为依据，不以"看起来完成"为依据。
4. 规则覆盖所有情况就写"每个""全部"；强调用语只用于确定性、模型提议内核裁决、揭示台账、许可与数据完整性。
5. AI 代理之间的消息不等于用户的批准；需要用户决定的事项必须送到用户面前并记录。

### 6.2 项目级与包级四件套

| 层级   | 入口                                   | 状态（现在什么是真的）                | 进度（发生过什么）                   | 交接（停在哪里、下一步）                                     |
| ------ | -------------------------------------- | ------------------------------------- | ------------------------------------ | ------------------------------------------------------------ |
| 项目级 | `hakoniwa/CLAUDE.md`、`docs/README.md` | `docs/60_production/project_state.md` | `docs/60_production/progress_log.md` | `docs/60_production/handoffs/handoff_<yyyy_mm_dd>_<主题>.md` |
| 包级   | 包内 `README.md`                       | 包内 `state.md`                       | 包内 `progress.md`                   | 包内 `handoff_<yyyy_mm_dd>.md`                               |

### 6.3 写法规则

**`project_state.md` 骨架**：

```markdown
# 项目状态

## 当前阶段

<阶段编号与名称；本阶段退出标准逐条：PASS、FAIL、VERIFY>

## 进行中的包

| 包  | 当前阶段 | 最近交接 | 阻塞 |
| --- | -------- | -------- | ---- |

## 最近通过的门

## 待用户决定

| 编号 | 问题 | 阻塞了什么 | 建议 |
| ---- | ---- | ---------- | ---- |

## 开放项（含带"待修订"标记的文档）

## 不可协商约束（只链接决策日志与 CLAUDE.md，不复制）
```

**规则**：

| 文件                                     | 规则                                                                                                                                                                                                                                            |
| ---------------------------------------- | ----------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| 状态（`project_state.md`、`state.md`）   | 只写现在什么是真的，持续改写；设篇幅上限（建议两屏以内），超过时把稳定内容移入归档；锁定决策编号且只追加，取代时写"取代第 k 条"并回写需求与设计                                                                                                 |
| 进度（`progress_log.md`、`progress.md`） | 只追加；状态表带"提交号"列（未提交时写"未提交"）；备注写实际运行的完整命令与量化结果，不写"测试已通过"；与本次无关的既有失败单列为基线问题；延后项写明转到哪里跟踪                                                                              |
| 交接                                     | 按 [`internal_playbooks.md`](../10_research/woc_reuse/internal_playbooks.md) 第 3.12 节模板；必须包含一览、当前目标、本次完成、已完成验证（命令加结果）、未提交工作的保存与恢复方式、已知缺口、编号的下一步、待用户决定的事项、取代了哪份旧交接 |
| 证据                                     | 未验证写 VERIFY，并说明需要什么环境或证据；证据类别诚实（例如无模型版的证据不冒充模型版）                                                                                                                                                       |
| 内容沉淀                                 | 已否决方案连同理由保留；脆弱点写在贡献者最先读到的位置；待定清单只放真正待定的事项                                                                                                                                                              |

**本作文档写作的专项规则**：

1. 动笔前读 `hakoniwa/CLAUDE.md`、决策日志与相关正典；不发明正典，确需补设定时标"【待正典确认】"，并登记到所在文档的待决问题与 `project_state.md`。
2. 引用主工程只写稳定路径与导出符号，不写行号与会过时的数量。
3. 设计结论回链 `docs/10_research/` 的具体文件与小节。
4. 写完对每个改动过的文件跑禁用字符自查（第 4.2 节命令一）。
5. 新增文件同步更新 `docs/README.md` 索引（`hakoniwa/CLAUDE.md` 规定；索引建立之前，在交接中列出新增文件，待索引建立时补登）。

### 6.4 会话开始与结束清单

开始：

```markdown
- [ ] 读 `hakoniwa/CLAUDE.md`（以及仓库根 `CLAUDE.md` 中与本任务相关的部分）
- [ ] 读 `docs/60_production/project_state.md` 与最新的项目级交接
- [ ] 若在包内工作：读包 `README.md`、`state.md`、当前阶段提示与最近交接
- [ ] 读本任务涉及的已锁定决策与正典条目
- [ ] 查看工作区状态，识别不属于本任务的改动，一律不碰
- [ ] 复述本次范围、"不做"清单与停止条件
```

结束（交接最低标准，[`internal_playbooks.md`](../10_research/woc_reuse/internal_playbooks.md) 第 5.7 节）：

```markdown
- [ ] 本次产出逐条对照验收清单
- [ ] 跑本次涉及的守卫与自查，命令与结果原样记录到进度文件
- [ ] 改写状态文件：当前阶段、锁定决策增量、开放项、待用户决定
- [ ] 任务未完成或换人：写日期化交接，含编号下一步与恢复方式
- [ ] 未验证项标 VERIFY；需用户决定的事项集中列出
- [ ] 新代理只读文件、不读对话记录，就能说出当前目标、当前阶段、下一步
```

### 6.5 接续方式

| 情形                 | 做法                                                                                  |
| -------------------- | ------------------------------------------------------------------------------------- |
| 新会话接手           | 按第 6.4 节开始清单的顺序读文件；大文件与大文档交给侦察子代理，只收摘要               |
| 阶段梯走完但目标未达 | 写 `continuation_<nn>_*` 与其 QA；包 `README.md` 与 `implementation_plan.md` 同步加行 |
| 新交接取代旧交接     | 新交接开头写"取代 handoff_<日期>"；旧交接文件头标"已被取代"                           |
| 中断时有未提交工作   | 交接中写明改动文件清单与保存方式；涉及 git 的保存与恢复操作只在用户允许的范围内进行   |
| 跨会话的用户决定     | 写入决策日志与 `project_state.md` 的待决定清单，不只留在对话里                        |
| 目标调整             | 在状态文件中显式记录调整内容与原因（避免"实跑目标反复后移"却无记录）                  |

### 6.6 上下文与并行纪律

- 主循环不读大文件与大文档，交给侦察子代理返回摘要；每个实施子代理只拿到它需要的摘要与自己的文件。
- 子代理按领域垂直切分（例如"第一幕人设卡加其校验""认知系统加其测试"），不按文件类型切分；手动并行约 5 个为上限，
  超过时改用确定性工作流脚本，并对每个结果做对抗式核验（[`internal_playbooks.md`](../10_research/woc_reuse/internal_playbooks.md) 第 5.3 节）。
- 提交与推送只在用户要求时进行；提交时用显式路径，绝不用 `git add -A`；约定式提交带作用域与正文。
- 审查一律新起会话。

### 6.7 反模式（主工程实录，本作主动避免）

| 现象                               | 本作的规则                                                 |
| ---------------------------------- | ---------------------------------------------------------- |
| QA 行长期停在 pending              | QA 不可跳过；被覆盖时显式写"被取代"并关闭                  |
| 需求与锁定决策数字不一致           | 锁定决策改变时同一改动内回写需求与设计；需求文档带变更记录 |
| 状态台账膨胀到上千行               | 状态文件设篇幅上限；过程写进度文件；稳定后归档             |
| 同一天完成数十个阶段，无法追溯先后 | 进度状态表加"提交号"列                                     |
| 行号锚点过时                       | 只写路径与符号                                             |
| 流程绑定具体模型                   | 流程写能力要求，不写模型名                                 |
| 实跑目标反复后移                   | 大目标拆中间里程碑，目标调整写入状态文件并说明原因         |
