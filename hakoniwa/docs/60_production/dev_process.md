# 研发流程（Dev Process）

> 归属：`docs/60_production/`（制作计划，正典优先级第 5 级）。与 `../00_vision/`、`../20_world/`、`../30_story/` 冲突时以后者为准，并回头修订本文。
> 作用：规定《箱庭纪》从正典到代码的文档分层与评审门、详细设计的组织、实施包流程、质量门与审查角色、正典变更流程、与 AI 代理长期协作的规则，以及文档计划表。
> 本文采纳 [internal_playbooks.md](../10_research/woc_reuse/internal_playbooks.md) 第 6 章的建议并定稿；采纳后，第 6 章仅作依据，以本文为准。
> 姊妹文档：[roadmap.md](roadmap.md)（里程碑与验收）、[development_plan.md](development_plan.md)（实施包清单）、[project_state.md](project_state.md)（现状）、[risks.md](risks.md)（风险）。
> 主要上游：决策日志的 D-057（代码在 `hakoniwa/`，实施包在 `docs/70_packets/`，原型以功能开关在 `src/` 内实现）、D-007、D-010、D-077；
> [release_engineering.md](../50_tech/release_engineering.md) 第 7、10、11 节（内容管线、测试、流水线与 `npm run gate`）；`hakoniwa/CLAUDE.md`（目录分工、正典优先级、文档规则）。

## 0. 一页结论

1. **八层文档加一条横向制作管理线。** L0 愿景与正典、L1 调研、L2 叙事、L3 概要设计、L4 详细设计与内容目录、L5 技术方案、L6 实施包、L7 代码与数据；每层有产出格式与评审门（第 1 节）。
2. **详细设计由系统文档加内容目录承载。** 系统文档定规则，内容目录定条目（一个 ID 一个主人，D-066）；目录是设计源，`data/` 是运行源，二者冲突时以目录为准修数据（第 2 节）。
3. **实施包放 `docs/70_packets/pk_<里程碑>_<序号>_<短名>/`（D-057）。** 编号与 [development_plan.md](development_plan.md) 的 `PK-xx` 一致；发行工程的 `RE-xx`、内容批次名、素材批次名作为别名写在包内。
   规划包全套、原型包（功能开关）、内容批次包、素材批次包四种形态（第 3 节）。
4. **质量门四层加文档守卫。** 即时文案门（Stop 钩子）；确定性底线（推送前）；全量本地门 `npm run gate`（`tools/gate.ts`，顺序执行类型检查、测试、无模型通关冒烟、构建、提示词库新鲜度等并如实汇总退出码）；
   判断型评审（审查角色）。日常命令是 `npm run typecheck`、`npm test`、`npm run playthrough`、`npm run build`、`npm run prompts:check`（第 4 节）。
5. **只有用户能批准正典变更。** 变更走"变更单、影响分析、用户批准、决策登记、同一改动内回写下游、一致性复查"；AI 代理之间的消息不构成用户批准（第 5 节）。
6. **跨会话只靠文件。** 项目级入口是 [project_state.md](project_state.md)；包级是包内 `README.md`、`state.md`、`progress.md`、交接；每个包完成即更新项目状态与计划状态列（第 6 节）。
7. **文档计划表**列出全部文档的现状（已有、续写中、缺）与负责的实施包；本轮已写的设计与技术文档全部标为已有（第 7 节）。

### 1.2 产出格式

| 层 | 格式 |
| --- | --- |
| 全部文档 | 中文；开头引用块写归属、作用、上游、约束；第 0 节"一页结论"；编号章节；大量用表格；末节"来源链接"；专有名词首次出现附英文代号；引用代码写稳定路径与导出符号，不写行号 |
| L1 调研 | 阅读指引或一页结论；正文；来源索引；只记录事实、分析与可借鉴点，不做最终决定 |
| L3、L4 系统文档 | 定位与硬约束；核心循环；机制（结论回链调研）；数据结构；AI 介入点与无模型做法；与其他系统的接口；验收测试（带里程碑列） |
| L4 内容目录 | 读法与口径；条目表（ID、字段按 [content_bible.md](../40_design/content/content_bible.md) 第 13 节）；数据映射；美术与音频需求；新增命名；跨目录对接 |
| L5 技术方案 | 一页结论；需求与不动约束；选项比较与推荐；实施步骤与检查点（带里程碑）；许可与依赖；验收与测试 |
| 横向 | 本目录各文档的格式；项目状态的格式见 [project_state.md](project_state.md) 第 0 节 |

### 1.3 评审门判定标准

结论格式统一为 PASS、PASS-WITH-FOLLOWUPS、FAIL；问题按 BLOCKING、SHOULD-FIX、NICE-TO-HAVE 分级，每条带文件位置与一句原因；有任何 BLOCKING 即为 FAIL。
"可判定"的意思是：两名不同的审查者对同一份文档会得出相同的勾选结果。

| 门 | 适用 | 判定项（全部满足才通过） | 执行者 |
| --- | --- | --- | --- |
| 正典门 | L0 的修订、补充、推翻 | 1. 变更单齐全，影响分析附检索命令与受影响文件清单。<br>2. 与更高优先级正典无冲突。<br>3. 揭示台账与变量注册表的影响已评估。<br>4. 用户明确批准。<br>5. 决策日志已登记。<br>6. 受影响下游已在同一改动内回写。<br>7. 禁用字符扫描为 0。 | 用户；正典一致性审查 |
| 调研入库门 | L1 新文档或大改 | 1. 每条事实可追溯到路径或链接。<br>2. 事实、补充、分析分开标注。<br>3. 不做最终决定。<br>4. 涉及复用时有许可提醒。<br>5. `docs/10_research/README.md` 索引已更新。 | 用户抽审 |
| 叙事门 | L2 新文档或大改 | 1. 通过 [narrative_design.md](../30_story/narrative_design.md) 的写作检查清单。<br>2. 新增线索在台账登记编号、层级、解锁条件。<br>3. 新增变量进入注册表（D-076）。<br>4. 新增命名进入术语表并完成原创性检索。<br>5. 正典一致性审查无 BLOCKING。 | 用户；正典一致性审查 |
| 概要评审门 | L3 | 1. 写明服务的支柱并回答"删掉它少了什么"。<br>2. 不与正典冲突。<br>3. 关键结论回链调研。<br>4. 接口与非目标写明。<br>5. 含 AI 的系统写明无模型做法。 | 用户；正典一致性审查 |
| 详细设计评审门 | L4 | 1. 规则与数值可测试，数值回链公式或注明依据（第 2.2 节）。<br>2. 状态机含失败、超时与兜底。<br>3. 每个 AI 介入点有模型做法与内置 AI 做法。<br>4. 数据结构带存档字段的默认值。<br>5. 验收测试编号可判定并带里程碑。<br>6. 条目 ID 一个主人，跨目录只按 ID 引用。<br>7. 没有未决的开放项。 | 用户；正典一致性审查；数值溯源审查 |
| 技术方案评审门 | L5 | 1. 逐条说明如何守住确定性、内核纯度、模型提议内核裁决、表现只读接缝。<br>2. 有选项比较与推荐。<br>3. 验收指标可测。<br>4. 依赖增减与许可已评审。 | 用户；模拟架构审查 |
| 实施包门 | L6 | 1. 每阶段 2 到 4 个交付物，超过 5 个即拆。<br>2. 第一阶段是地基。<br>3. 每阶段有"不做"清单与停止条件。<br>4. 验证命令可直接运行。<br>5. 评审派发矩阵全包只有一份。<br>6. 实现阶段与 QA 阶段成对。<br>7. 阶段提示自包含，新会话粘贴即可执行。 | AI 生成；用户确认 |
| 阶段门 | 每个实施阶段 | 1. 验收清单逐条勾选。<br>2. 验证命令全绿，命令与结果原样记录在 `progress.md`。<br>3. 派发的审查无 BLOCKING。<br>4. `progress.md` 与 `state.md` 已回写。 | 新起会话的 QA 代理 |
| 里程碑门 | M0 到 M6 与其内部检查点 | 1. 证据台账无空白状态。<br>2. 末次代码或内容变更之后的一次完整实跑通过（[development_plan.md](development_plan.md) 第 9 节）。<br>3. 风险登记已复查。<br>4. [project_state.md](project_state.md) 已更新。<br>5. 里程碑结论写进决策日志。 | 用户；总闸审查 |

### 1.4 文档状态与生命周期

| 状态 | 含义 |
| --- | --- |
| 草案 | 正在写，可大改 |
| 评审中 | 已提交评审门 |
| 已定稿 | 过门；之后的修改按本层评审门重新过门 |
| 历史 | 描述已完成的工作或已封包的包，只能当记录读 |
| 已废弃 | 被取代，文件头写明取代者 |

- 文档只写当前方案，不写修改记录；git 历史就是修改记录（`hakoniwa/CLAUDE.md`）。
- 目标设计不冒充现状：现状写在 [project_state.md](project_state.md)；实现期设计与代码冲突时，先以代码为准核实现状，再按正典优先级决定改代码还是改设计；正典与设计冲突时一律以正典为准。

## 2. 详细设计的组织

### 2.1 设计源与运行源

| 对象 | 设计源 | 运行源 | 一致性 |
| --- | --- | --- | --- |
| 规则与公式 | 系统文档（`docs/40_design/systems/`、成长、注册表、界面、音频） | `src/systems/`、`src/core/` | 测试钉住设计文档的验收行；文档改了，测试同一改动更新 |
| 内容条目 | 内容目录（`docs/40_design/content/`，D-066） | `data/<领域>/*.json` | 内容导入批次（第 3.5 节）抽取、补字段、过 V1 到 V10 后合入；两者冲突时以目录为准修数据，数据层发现的设计问题登记回 [content_review.md](../40_design/content/content_review.md) |
| 世界状态变量 | [world_state_registry.md](../40_design/world_state_registry.md) | `data/registry/vars.json`（`tools/registry/build.ts` 生成） | 生成脚本与校验保持一致；新变量先登记再使用 |
| 地图 | 地图简报与图集 | `data/world/`、地图数据 | 每张图上线时同步地图数据、图集状态与路线（[map_briefs.md](../40_design/world/map_briefs.md) 第 15 节） |
| 素材 | 提示词库规格文件 `assets/prompts/specs/` | `assets/processed/` 与图集 | 编号三方一致（目录、规格、素材清单）；素材覆盖测试 |
| 文本 | 内容数据中的中文与 `locales/zh-Hans/` | 字符串表 | 文本键（D-077）；文本检查 |

篇幅超过一次可读完的系统文档按节拆成同名目录（`systems/<系统>/`），原文件保留为目录的入口与一页结论；拆分时节号不变。

### 2.2 数值溯源写法

每个数值写明来源之一：经典公式（写公式名与出处）、正典（写文档与节号）、本作推导（写推导式与输入）、实测（写测量的包与证据位置）。
平衡调整只改数据，不改公式；调整理由写进批次报告。

## 3. 实施包流程

### 3.1 位置与命名

| 对象 | 位置 | 命名 |
| --- | --- | --- |
| 实施包（全部形态） | `docs/70_packets/pk_<里程碑小写>_<两位序号>_<英文短名>/` | 例如 `pk_m0_14_text_ref_kernel`、`pk_m1_29_act1_lines`；编号与 [development_plan.md](development_plan.md) 一致 |
| 别名 | 包 `README.md` 首行 | 发行工程编号（例 `RE-13`）、内容批次名（例 `content_act1_lines_01`）、素材批次名（例 `art_m1_monsters_01`）、内置 AI 步号 |
| 原型 | 不设原型目录（D-057）；原型在 `src/` 内以功能开关实现 | 开关名 `proto.<pt_编号>.<短名>`；结论写进决策日志后收口或转正 |
| 内容暂存 | `data/_staging/<内容批次名>.json` | 不被内核加载，合入后清空 |
| 包内文件 | 见第 3.2 节 | 一律小写加下划线；唯一例外是 `README.md` |
| 里程碑证据台账 | `docs/60_production/milestones/<里程碑>/verification_matrix.md` | 每个里程碑一份 |

### 3.2 文件集合与职责

| 文件 | 回答什么 | 何时写 | 生命周期 |
| --- | --- | --- | --- |
| `README.md` | 这是什么包、别名、从哪读起 | 立项时 | 活文档 |
| `brainstorm.md` | 为什么做、已有什么、可能怎么做 | 侦察之后 | 规划期活文档，之后转历史 |
| `requirements.md` | 做成什么样才算对（引用设计文档的条目与验收行，不复制正文） | brainstorm 被用户认可后 | 活文档 |
| `design.md` | 怎么搭 | requirements 之后 | 活文档 |
| `implementation_plan.md` | 分几步做；评审派发矩阵（全包唯一一份） | design 之后 | 活文档 |
| `phase_<nn>_<slug>.md` 与 `phase_<nn>_qa.md` | 这一步做什么、怎么验 | 实施计划之后，批量生成 | 执行前后不改，作为承诺凭证 |
| `continuation_<nn>_<slug>.md` 与 QA | 阶段梯走完但目标未达时如何续推 | 需要时 | 同上 |
| `verification_matrix.md` | 凭什么说做完了（每条验收的命令、结果与证据位置） | 收官前 | 交付凭证 |
| `progress.md` | 做到哪了、每步发生了什么（带提交号列） | 每个阶段结束 | 只追加 |
| `state.md` | 现在什么是真的 | 每个阶段结束 | 持续改写，设篇幅上限 |
| `handoff_<yyyy_mm_dd>.md` | 上一位停在哪里，下一步做什么 | 会话中断、换人、长任务暂停 | 日期化快照，被新交接取代 |

小包（量级不超过 2 个代理人日）可以只写 `README.md`、`verification_matrix.md`、`progress.md` 三件，规则与验收直接引用开发计划的包行。

### 3.3 流转

| 步 | 输入 | 产出 | 出口标准 |
| --- | --- | --- | --- |
| 0 立项 | 开发计划的包行 | 包 `README.md` | 目标一句话说清；依赖包已完成；[project_state.md](project_state.md) 第 4 节加一行，计划状态写成"进行中" |
| 1 侦察 | 目标、设计文档、代码库 | 侦察摘要 | 无法核实的事项标为 OPEN 并列为阻塞项，不得猜测 |
| 2 brainstorm | 侦察摘要 | `brainstorm.md` | 用户认可总体方向（小包可跳过） |
| 3 requirements | brainstorm | `requirements.md` | 每条需求可观察、可验证，并引用设计文档编号；非目标写明 |
| 4 design | requirements | `design.md` | 每条需求有承载模块；内核裁决边界与状态来源写清 |
| 5 实施计划 | design | `implementation_plan.md` | 过实施包门 |
| 6 阶段提示 | 实施计划 | `phase_<nn>_*.md` 与 QA | 自包含 |
| 7 实施 | 阶段提示、`state.md` | 代码、数据、测试、文档回写 | 阶段验收清单全勾；验证命令全绿；派发的审查无 BLOCKING |
| 8 QA | 阶段提示与改动 | 审计结论与修复 | 无 BLOCKING |
| 9 回写 | 实施与 QA 结果 | `progress.md`、`state.md` | 下一阶段只读 `state.md` 即可起步 |
| 10 交接 | 会话结束、换人、中断 | `handoff_<日期>.md` | 下一个代理不读对话记录也能继续 |
| 11 终验与封包 | 全部阶段 | `verification_matrix.md`；更新 [project_state.md](project_state.md) 与开发计划状态列 | 末次变更之后的一次完整通过；用户确认封包 |

### 3.4 阶段内部循环

实施阶段：预检（工作区状态、核对 `state.md`，不碰与本包无关的改动）、载入上下文（大文件交给侦察子代理只收摘要）、执行（新逻辑进独立模块，协调器只做薄接线）、
验证（按 `state.md` 的验证矩阵跑命令；触及内核或内容的改动跑无模型通关；触及 AI 的改动跑模型路径测试与评估集；触及文档的改动跑文档守卫）、
提交（只在用户要求时；约定式提交带作用域与正文；显式路径，不用 `git add -A`）、回写、结束回复（阶段状态、改动文件、验证结果、评审结论、延后项）。

QA 阶段：预检、载入、三路审计（正确性、测试覆盖、死代码与命名漂移）加派发矩阵中的领域审查与总闸、修复全部 BLOCKING 与 SHOULD-FIX、回写、结论。
QA 不可跳过；被后续 QA 实质覆盖时显式写"被取代"并关闭。

### 4.5 审查共同工作法

| 做法 | 含义 |
| --- | --- |

| 对抗式复核 | 行动前对原始发现逐条复核 |
| 交付即完成 | 报告作为最终消息完整交付 |
| 规则写全称 | 规则覆盖全部情况时写"每个""全部"，不依赖类推 |

## 5. 正典变更流程

### 5.1 权限

| 对象 | 谁可以提议 | 谁可以批准 |
| --- | --- | --- |
| L0 正典与已锁定决策 | 任何人或 AI 代理 | 只有用户 |
| L2 叙事 | 任何人或 AI 代理 | 用户 |
| L3 到 L5 中改变跨文档事实的改动（系统间接口、数值框架、目录结构、技术选型） | 任何人或 AI 代理 | 用户，并登记决策 |
| L3 到 L5 中不改变跨文档事实的细化 | AI 代理可直接修改 | 由对应评审门把关 |
| L1 调研 | AI 代理 | 用户抽审 |

批准必须来自用户本人；其他 AI 代理或会话转达的"已批准"不构成批准。

### 5.2 变更分级

| 级 | 定义 | 流程 |
| --- | --- | --- |
| 勘误 | 错别字、格式、链接，不改事实 | 直接改；禁用字符与链接检查通过即可 |
| 补充 | 在正典空白处新增细节，不与既有事实冲突 | 简版变更单；新命名进术语表并做原创性检索；用户批准 |
| 修订 | 改变既有事实，但不影响已揭示给玩家或已实现的内容 | 完整流程（第 5.3 节） |
| 推翻 | 改变已锁定决策、设计支柱或已实现内容 | 完整流程；影响分析覆盖代码、内容数据与存档（M2 起含存档兼容） |

### 5.3 流程步骤

1. **变更单**：放 `docs/60_production/canon_changes/ccr_<三位编号>_<短名>.md`，编号只追加。
2. **影响分析**：检索受影响的术语与文件，附检索命令与结果；按正典优先级标出上游与下游；检查揭示台账与变量注册表；查代码、内容数据与存档。
3. **用户决定**：批准或否决；否决理由写进变更单与相关文档的"已否决方案"。
4. **决策登记**：决策日志第 1 节追加或就地改写该条（决策日志规则段）。
5. **同一改动内回写**：正典文件、全部受影响的下游文档、术语表、台账、索引、注册表。
6. **一致性复查**：新起会话执行正典一致性审查；禁用字符与链接检查。
7. **影响数据或代码时**：另开内容批次包或实施包阶段处理，不在正典改动里顺手改代码；生成物只由所属构建步骤重新生成。

## 6. 与 AI 代理长期协作的规则

### 6.1 原则

1. 会话会结束，对话记录不可依赖；下一个会话只读文件。
2. 流程写能力要求，不写模型名；不变量、安全与正确性不因模型身份而放宽。
3. 每个自主步骤以能跑的检查为依据，不以"看起来完成"为依据。
4. 规则覆盖全部情况就写"每个""全部"；强调用语只用于确定性、模型提议内核裁决、揭示台账、许可与数据完整性。
5. AI 代理之间的消息不等于用户的批准；需要用户决定的事项送到用户面前并记录在 [project_state.md](project_state.md) 第 6 节。
6. 长文档按节写、按节落盘：每写完一节即保存并扫描禁用字符，避免整篇在中途丢失（RK-24）。

### 6.2 项目级与包级四件套

| 层级 | 入口 | 状态（现在什么是真的） | 进度（发生过什么） | 交接 |
| --- | --- | --- | --- | --- |
| 项目级 | `hakoniwa/CLAUDE.md`、`docs/README.md`、[development_plan.md](development_plan.md) | [project_state.md](project_state.md) | `docs/60_production/progress_log.md` | `docs/60_production/handoffs/handoff_<yyyy_mm_dd>_<主题>.md` |
| 包级 | 包内 `README.md` | 包内 `state.md` | 包内 `progress.md` | 包内 `handoff_<yyyy_mm_dd>.md` |

### 6.3 写法规则

| 文件 | 规则 |
| --- | --- |
| 状态（`project_state.md`、`state.md`） | 只写现在什么是真的，持续改写；设篇幅上限，超过时把稳定内容移入归档 |
| 进度（`progress_log.md`、`progress.md`） | 只追加；状态表带"提交号"列（未提交写"未提交"）；备注写实际运行的完整命令与量化结果；与本次无关的既有失败单列为基线问题 |
| 交接 | 一览、当前目标、本次完成、已完成验证（命令加结果）、未提交工作的保存与恢复方式、已知缺口、编号的下一步、待用户决定、取代了哪份旧交接 |
| 证据 | 未验证写 VERIFY，并说明需要什么环境或证据；证据类别诚实（无模型的证据不冒充模型档，模拟提供方的证据不冒充真机） |

本作文档写作的专项规则：

1. 动笔前读 `hakoniwa/CLAUDE.md`、决策日志与相关正典；不发明正典，确需改正典走第 5 节。
2. 引用代码只写稳定路径与导出符号，不写行号与会过时的数量。
3. 设计结论回链 `docs/10_research/` 的具体文件与小节。
4. 写完对每个改动过的文件跑禁用字符自查（第 4.3 节命令一）。
5. 只写当前方案，不写修改记录措辞。
6. 新增文件同步更新 `docs/README.md` 索引。

### 6.4 会话开始与结束清单

开始：

```markdown
- [ ] 读 `hakoniwa/CLAUDE.md`（以及仓库根 `CLAUDE.md` 中与本任务相关的部分）
- [ ] 读 `docs/60_production/project_state.md` 与最新的项目级交接
- [ ] 若在包内工作：读包 `README.md`、`state.md`、当前阶段提示与最近交接
- [ ] 读本任务涉及的已锁定决策与设计条目
- [ ] 查看工作区状态，识别不属于本任务的改动，一律不碰
- [ ] 复述本次范围、"不做"清单与停止条件
```

结束：

```markdown
- [ ] 本次产出逐条对照验收清单
- [ ] 跑本次涉及的守卫与自查，命令与结果原样记录到进度文件
- [ ] 改写状态文件；包完成时同一改动更新 project_state.md 与 development_plan.md 的状态列
- [ ] 任务未完成或换人：写日期化交接，含编号下一步与恢复方式
- [ ] 未验证项标 VERIFY；需用户决定的事项集中列出
- [ ] 新代理只读文件、不读对话记录，就能说出当前目标、当前里程碑、下一步
```

### 6.5 接续方式

| 情形 | 做法 |
| --- | --- |
| 新会话接手 | 按第 6.4 节开始清单的顺序读文件；大文件交给侦察子代理，只收摘要 |
| 阶段梯走完但目标未达 | 写 `continuation_<nn>_*` 与其 QA；包 `README.md` 与 `implementation_plan.md` 同步加行 |
| 新交接取代旧交接 | 新交接开头写"取代 handoff_<日期>"；旧交接文件头标"已被取代" |
| 中断时有未提交工作 | 交接中写明改动文件清单与保存方式；涉及 git 的保存与恢复只在用户允许的范围内进行 |
| 跨会话的用户决定 | 写进决策日志与 `project_state.md`，不只留在对话里 |
| 目标调整 | 在状态文件中显式记录调整内容与原因 |

### 6.6 上下文与并行纪律

- 主循环不读大文件，交给侦察子代理返回摘要；每个实施子代理只拿到它需要的摘要与自己的文件。
- 子代理按领域垂直切分（例如"第一幕人设卡加其校验""认知系统加其测试"），不按文件类型切分；手动并行约 4 条线（[development_plan.md](development_plan.md) 第 6.2 节），
  超过时改用确定性工作流脚本并对每个结果做对抗式核验。
- 多个代理同时工作时，每个代理只写分配给它的文件；对别人文件的改动写成请求回写，由负责方落地。
- 提交与推送只在用户要求时进行；本仓库只在 `main` 上工作（D-057），提交时用显式路径，约定式提交带作用域与正文。

### 6.7 反模式

| 现象 | 本作的规则 |
| --- | --- |
| QA 行长期停在待办 | QA 不可跳过；被覆盖时显式写"被取代"并关闭 |
| 需求与锁定决策数字不一致 | 锁定决策改变时同一改动内回写需求与设计 |
| 状态台账膨胀到上千行 | 状态文件设篇幅上限；过程写进度文件；稳定后归档 |
| 同一天完成数十个阶段，无法追溯先后 | 进度状态表加"提交号"列 |
| 行号锚点过时 | 只写路径与符号 |
| 长文档写到一半丢失 | 按节落盘（第 6.1 节第 6 条） |
| 实跑目标反复后移 | 大目标拆中间检查点，目标调整写进状态文件并说明原因 |
