# PK-M0-14 内核文本键迁移：逐批金样报告

> 发行工程第 8.4 节第 5 步：事件里的文字从字符串变成对象，原样的世界哈希必然改变，因此每批不比原样哈希，而是把文字渲染回中文后再比。本文记录方法与四批结果。入口见 [README.md](README.md)。

## 1. 方法

- **跑什么**：无模型档、种子 `20261115`（与 `tests/playthrough/harness.ts` 的 `SEED` 相同），自动玩家各走一遍两条结局路线 `release`（离手）与 `rule_merca`（梅尔卡之治），直到结局。
- **记什么**：`tests/playthrough/text_golden.playthrough.test.ts`（默认跳过，设 `TEXT_GOLDEN_OUT` 才运行）在每批事件派发后，先把事件里的每个 `TextRef` 用 `locales/zh-Hans/` 的表渲染成中文（内容键经内容查找），再按排序键的规范 JSON 计哈希：
  - 自动玩家的结果（结局、是否完成、tick 数、死亡数、完成的任务、各幕起止、命令计数）；
  - 事件流：总数与总哈希、按事件种类的计数与哈希、每 20000 tick 一个窗口的哈希；
  - 每次换幕时与结局时的世界：每个系统切片、元数据、AI 请求状态各一个哈希；结局时的全部旗标原值。
- **怎么比**：`node tools/i18n/golden_diff.ts <迁移前.json> <迁移后.json>`，逐项比较（耗时不比）。渲染后的中文必须等于旧字面量，所以只要文字以外有任何差别（多一个事件、一个数值、一次随机抽取、一个切片字段），对应的哈希就会不同。
- **迁移前的基线**：开工时把 `src/`、`data/` 与金样测试复制到临时目录，在副本上跑出基线；每批完成后同样先复制当时的工作区再跑，因此并行工作的其他包后来改动的数据与历法（`data/combat/monsters.json`、`data/strategy/config.json`、`src/core/time.ts`）不在任何一份快照里，比较只反映本包的改动。
- **灵敏度**：迁移后的世界与事件里有大量 `TextRef`（见第 3 节的计数）；若渲染没有生效或有一个参数、一个字没对上，对应事件种类与切片的哈希就会不同。

## 3. 渲染覆盖

在 B4 快照上用同一种子让自动玩家跑 400000 tick（到第一幕）：世界与事件里共有 9728 个 `TextRef`，渲染后剩 0 个，缺键与缺参 0 处。说明迁移后的状态里确实满是文本引用，金样的"一致"不是因为没有可渲染的东西。

## 4. 收尾一轮与并行改动

- **与 PK-M0-29 的关系**：12:00 前后，并行的 PK-M0-29（历法每季 91 日、经验与首领等级规则、`data/` 数值）把有意的玩法改动放进了同一个工作区。本报告的基线与四批快照都早于这些改动：快照里的 `src/core/time.ts`、`src/systems/combat/threat.ts`、`data/combat/monsters.json`、`data/strategy/config.json` 与基线逐字节相同（按文件哈希核对），所以四批的比较只含本包的改动，不需要重录基线。
- **收尾快照**：B4 之后本包还改了内核（拒绝原因收窄为 `TextRef`；`commandText` 让模型写的文字存为 `{ raw, lang }`、拒收模型给的文本键并给规则回退的长句加截断；`no_handler` 改为英文原文；`isTextRef` 只认带作用域的键；渲染器不再因畸形参数抛错）。为了只比本包的改动，把这些文件覆盖到 B4 快照上（其余文件仍是 PK-M0-29 之前的样子）再跑两条路线，与同一基线比较，结果见第 2 节"收尾"行。
- 当前共享工作区上 `npm run playthrough` 的两条路线在第二幕卡住（第二幕始于 tick 558750，基线为 520824），分叉来自 PK-M0-29 的升级与经验改动，与文字无关；本节的叠加快照正是为把两者分开。
- 角色包题面移入 `src/game/ai_roles/templates/` 后，十个角色包、通则与输出格式的组装结果与移动前逐字节相同（移动前后各导出一次比较）；它们只在接模型时使用，不影响无模型档。
